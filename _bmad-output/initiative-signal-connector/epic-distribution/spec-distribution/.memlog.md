topic: Installing and running SignalConnector from a public distribution (npm package or GitHub release zip) with a guided first run
updated: 2026-10-15T18:44
---


- (direction) User intent: make the product maximally accessible so a new person can take a zip from GitHub or an npm package, install it and use it, with no repo clone and no hand-edited files.
- (note) Current packaging gaps: package.json private=true, no files/main/exports/license/repository fields, no LICENSE, no CI, no CHANGELOG.
- (note) Install path today is Windows-only PowerShell: setup.ps1, ensure-java.ps1, install-signal-cli.ps1, link-device.ps1, run.ps1. Java 25 and a manual signal-cli download are prerequisites; the opencode plugin is copied into the global plugins dir by start-all.ps1.
- (note) Secrets use DPAPI through powershell.exe; non-Windows falls back to an in-memory store, so linked credentials do not survive a restart there.
- (capability) CAP-1 A person without a repo clone installs from a distribution channel (npm package or GitHub release zip) on a supported OS and gets a working signal-connector command.
- (capability) CAP-2 A guided first run takes a newcomer from install to a working bridge without hand-editing files: prerequisites detected, device linked by QR, config written, plugin installed, loop proven by one real message.
- (capability) CAP-3 Missing prerequisites are diagnosed with actionable instructions (what, where to get it, the exact command) instead of failing later mid-run.
- (capability) CAP-4 The normal install and run path works on Windows, macOS and Linux; secrets persist on all three without Windows-only facilities.
- (capability) CAP-5 Installing and updating the opencode plugin is a product command that reports its version, not a manual copy.
- (capability) CAP-6 One version tag produces both release artifacts (npm package and GitHub zip) from the same commit with the test suite green on all supported OSes.
- (constraint) Node >= 20 and no native build dependencies anywhere in the install path (AGENTS.md dependency rule).
- (constraint) Signal side stays a linked secondary device: the operator must scan a QR with their phone; there is no bot number or API token path.
- (constraint) Existing architecture is untouched: core/ imports no adapter, one SQLite DB is the single source of runtime state, secrets never in the repo or logs.
- (constraint) The Windows path that works today must not regress while the cross-platform path is added.
- (constraint) signal-cli is an external program with its own release and Java requirement; the product detects and can fetch it but does not vendor it.
- (decision) Non-goal: no hosted service or cloud relay; everything runs on the operator machine.
- (decision) Non-goal: no GUI, tray or service packaging in this sprint (already deferred in the spine).
- (decision) Non-goal: no agent adapter other than opencode.
- (decision) Non-goal: no distribution channels beyond npm and the GitHub release zip (no Homebrew, Chocolatey, winget, Docker).
- (decision) Non-goal: no multi-user, team or multi-tenant features.
- (assumption) The newcomer has Node >= 20, an opencode installation, a Signal account with a phone for linking, and is willing to use a terminal.
- (assumption) Public distribution is intended, so a public repository and a LICENSE are acceptable and required.
- (assumption) Requiring Java for signal-cli is acceptable for this sprint when it is detected and explained; bundling a runtime is deferred.
- (question) Which npm name and scope may be published? signal-connector is very likely taken on the public registry.
- (question) Is Java + signal-cli acceptable as a prerequisite for the first release, or must the release bundle a runtime?
- (question) Which operating systems must the first release support: Windows only first, or Windows and Linux together?
- (question) Which LICENSE, and is the repository public as part of this sprint?
- (question) Does the opencode plugin ship inside the main package (preferred) or as a second package?

- (direction) User instructed: resolve the open questions from the code where it answers, otherwise apply the best suggestion.
- (decision) npm name: keep `signal-connector`. Registry lookup on 2026-10-15 returned 404 (free) for signal-connector, opencode-signal-connector and signal-connector-cli; `opencode-signal` is taken by an unrelated package. No scope is needed.
- (decision) License and repository: MIT from a public repository in this sprint. Nothing in the code rules another license in; MIT is the least friction for a tool others are asked to install, and npm expects a license field it does not have today (package.json has private=true and no license).
- (decision) Operating systems: Windows, macOS and Linux. Evidence from the code: config.ts already falls back from APPDATA to ~/.config, spawnCommand.ts has a win32 branch and passes through elsewhere, link.ts branches on win32 and darwin; the only Windows-only piece is secrets.ts (DPAPI through powershell.exe), which entry 7 replaces.
- (decision) Java and signal-cli stay external prerequisites that are detected and fetched per platform, never bundled: scripts/install-signal-cli.ps1 already downloads signal-cli and scripts/ensure-java.ps1 installs a JDK, so fetching is the established pattern; no bundling machinery exists and vendoring a runtime contradicts the no-native-dependency constraint.
- (decision) The opencode plugin ships inside the same package, version-locked to it: plugins/signal-connector.ts already lives in the repository and start-all.ps1 copies it into the user plugins directory, so the package can carry it and install it as entry 6 does.

- (decision) Node floor raised from 20 to 22.13 (2026-10-15). Building the packaging entry disproved the earlier floor: src/store/sqliteDriver.ts:26 requires node:sqlite at module scope, src/index.ts imports the store, and on Node 20 that import dies with ERR_UNKNOWN_BUILTIN_MODULE before any CLI argument handling runs. node:sqlite exists from 22.5.0 and is unflagged from 22.13.0/23.4.0 (nodejs/node#55890 "unflag sqlite module"), so 22.13 is the honest floor; package.json engines.node is now >=22.13.0 and the success signal names 22.13.
