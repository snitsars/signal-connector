topic: On-demand avatar meeting: a command in a project Signal group yields a Google Meet link and a local avatar to talk to, while text stays in Signal
updated: 2026-10-16T23:25
---


- (direction) Operator asked for on-demand live conversations: a command in a project Signal group should produce a Google Meet link and an avatar to talk to in real time, while all text stays in Signal.
- (decision) Text stays in Signal; the meeting is an extra console for the same project session, so the Signal command, menu and approval loop is untouched.
- (decision) Meeting platform is Google Meet for this spec: a live video avatar is possible in a room, and Meet needs no API key, no SDK app and no fee, where Zoom needs an SDK app plus a native SDK (evidence: Zoom Meeting SDK raw video and virtual mic injection; open-source Meet bots driving a browser with fake media).
- (decision) Messenger calls are out on evidence: signal-cli call audio needs signal-call-tunnel, a Rust binary with a Unix control socket and PulseAudio or BlackHole devices; the Telegram Bot API cannot make or receive calls; WhatsApp calling needs the hosted Business Calling API with a Meta business account.
- (decision) The face and the voice stay local: avatar rendering, transcription and synthesis happen on the operator machine, with no hosted bot service and no third-party voice API.
- (decision) The room is created per command so the link is fresh from the chat; one fixed personal room stays as the fallback when Google credentials are absent.
- (capability) CAP-1 summon a meeting from the project chat: one command in the project group returns a join link whose room belongs to that project, and an unknown project or a second concurrent request is refused with the reason.
- (capability) CAP-2 the avatar is present and readable: it appears in the participant list under the project name within the join budget and its face shows the working, fine or needs-attention state during the task.
- (capability) CAP-3 spoken conversation in project context: a spoken question is answered aloud from the same session the text loop uses, so the answer matches what Signal would produce.
- (capability) CAP-4 text stays authoritative: approvals and commands typed in Signal during a meeting are honoured by the agent, and each meeting ends with exactly one summary message in that group.
- (capability) CAP-5 local by construction: with only the network to Google, a full meeting runs with no third-party account besides the operator Google one, and no credential, link or transcript reaches the repository or a log line.
- (capability) CAP-6 clean end: the stop command or the operator leaving makes the connector leave within the stop budget, frees the project for the next meeting, and reports a join failure in the group with the reason.
- (constraint) Signal remains the only text channel and no calls are added to any messenger, which is what forces the meeting platform route rather than an in-chat call.
- (constraint) Voice and face are produced locally: transcription, synthesis and rendering run on the operator machine or as fetched external tools, never a hosted API.
- (constraint) Google is authorised once with OAuth and the refresh token lives in the secrets store (spine AD-9); tokens, meeting links and transcripts never appear in the repository or a log line.
- (constraint) Core stays transport-agnostic (spine AD-1): the meeting and the voice arrive as new ports, so src/core gains no browser, audio or Google dependency.
- (constraint) One meeting per project at a time, because the project has one agent session; a second request is refused rather than shared.
- (constraint) Speech is acknowledged within about two seconds even when the task needs minutes, which forces an immediate spoken filler plus an asynchronous result.
- (constraint) Windows first and no native build on the install path: browser automation plus fetched tools (a transcription model, a system voice), the way signal-cli is fetched today.
- (assumption) The operator has a Google account able to create Meet rooms and will authorise it once.
- (assumption) A Chromium-based browser is available and a visible window during a meeting is acceptable.
- (assumption) The phone can open a Meet link from Signal through the Meet app or a mobile browser.
- (assumption) Phone and machine both reach Google directly, so unlike the local page option no LAN exposure of the connector is needed.
- (question) How is the room created: the Meet API with OAuth (recommended), a Calendar event with a conference link, the driven browser opening meet.new, or one fixed personal room in config?
- (question) Which local voice pair: Windows SAPI synthesis plus a fetched transcription model (recommended), or Piper plus whisper.cpp?
- (question) May a spoken yes or no approve a permission during a meeting, or do approvals stay text-only in Signal?
- (question) Does the avatar need a distinct per-project name and picture in the participant list, and are live captions wanted in the meeting?
- (question) Must a meeting survive a connector restart by rejoining, or is best-effort acceptable?
- (note) Non-goals fixed: no messenger calls, no Zoom or Teams in this spec, no operator video, no recording or transcript artifact, no hosted bot service, no multi-tenant, no scheduling, no calendar entries, and other humans are admitted by the operator in Meet rather than invited by the connector.

- (direction) Operator resolved the open questions: one fixed room with rejoin, and every recommendation accepted.
- (decision) One configured room instead of a room per command: the operator joins a single known room, so the connector needs no Google credentials, no Cloud project and no API call, and can rejoin after any interruption without creating anything. Creating a fresh room per request is deferred, not dropped.
- (decision) The connector rejoins: the active meeting lives in the store (project, room, started at, last activity) and after a restart or a browser crash it returns to the same room once when the meeting was active within 30 minutes, announces it in the group, and is cancelled by /meet stop. The conversation is not resumed mid-sentence.
- (decision) The likely interruption is the browser window dying rather than a service restart, and it uses the same rejoin path, which is why the meeting state is persisted even though the store already needs it for the one-meeting guard and the closing summary.
- (decision) Approvals stay text-only in Signal: anyone admitted to the room can speak, so a spoken word is not an authenticated identity, while Signal text comes from the operator own account. The avatar announces a waiting permission aloud and points at the group.
- (decision) Local voice pair fixed: the Windows system voice for synthesis and a fetched whisper model for transcription, consistent with fetching signal-cli instead of bundling it.
- (decision) The avatar is named after the project in the participant list; a per-project picture is not possible because the meeting takes it from the account, and live captions are not built by us because the platform already offers them as a viewer setting.
- (constraint) The room is configured, never created: this spec needs no Google credentials, no Cloud project and no API scope, and rejoin therefore works without any authentication.
- (constraint) One meeting at a time, because there is one room; a second request while a meeting runs is refused with the reason, whichever project asks.
- (constraint) Approvals are text-only: a spoken approval is refused because anybody in the room can speak, and the text path is the authenticated one.
- (constraint) The active meeting is persisted in the store so it can be rebuilt after a restart, the same rule the rest of the runtime follows (the database is the single source of runtime state).
- (capability) CAP-7 survive an interruption: after a service restart, a browser crash or a machine wake the connector returns to the same room once within the activity window, says so in the group, and the operator keeps talking with no new link.

- (direction) Operator asked the room for protection variants across three sessions, then to write the story and start building.
- (decision) Command surface is /meet <link> plus /meet stop. Bare /meet against a configured room is deleted and the room link stops being configuration.
- (decision) The pasted link is the authorisation: typed by the operator, in that project own group, resolved as (source path, sender) where the sync path sender is the channel and counts as the operator own linked device while the data path matches the number or ACI. The join message is a notice, never a confirmation.
- (decision) Accepted identities are configuration: one enumerated entry per project (ACI or uuid, number as a label, revocation date), never a directory; an empty list is fail-closed; the entry exists so that not authorised is a different answer from unknown, and so a second number can be granted instead of becoming an outage.
- (decision) The durable thing is a Meeting row (project, started, closed, outcome). The join URL and the room id are a credential: they live in that row and in the browser address bar and never in a log line, refusal or group message, and are wiped the instant the meeting stops being open, including on restart because rejoin is deferred. The row survives /meet stop while a task still runs, so the summary still lands.
- (decision) Validation (https, canonical parse, provider host allow-list, liveness probe) and the single-meeting claim are one store write committed before the browser opens. The claim keys on the open meeting rather than on the URL, so a repeated paste loses the race and is told which project holds the slot and since when.
- (decision) The browser joins as an anonymous guest with no Google profile and no credentials at all, into a host-locked room the operator created with knocking on. Admission is the operator sole act, nothing is auto-admitted, and being absent from the participant list is acceptable.
- (decision) Who is in the room is unverifiable and the contract says so: every occupant including the operator is an untrusted voice, the only authenticated identity in the system is the Signal text channel of the project group, and admitting a second human degrades the meeting to listen-only.
- (decision) The room may only propose: no voice, display name, participant entry, nonce or room event may attach the session or carry a command, approval or stop to the agent. The session attaches on the authorised join and speech is published only when spoken to.
- (decision) Liveness has two directions rather than one sensor: inbound deafness by a single AnalyserNode RMS on the copied room audio polled every five seconds, which doubles as the energy gate that drops a transcriрted sentence dreamed over room tone; outbound deafness later by the two-second acknowledgement acting as a probe. Presence is advisory telemetry with three outcomes plus a named presence-unknown state when the list is unavailable: never a block, never an identity, never an approval.
- (decision) CAP-7 (survive an interruption) is retired into non-goals as a named deferral and its id is never reused; CAP-8 replaces it: there is no silent deafness. Every declared guard must post in the project group or raise a health signal when it fails, and every stored active meeting must reach exactly one terminal outcome, a confirmed announced rejoin or a posted rejoin-failed reason with the row cleared, with a stale active row a hard failure surfaced in the group and the health check rather than only a log line.
- (decision) First slice in build order: the join tracer (anonymous guest join, three-colour canvas face, stop, one summary), the gate (identities, parse, probe, atomic claim, refusals, wipe), the voice loop (capture, local transcription, same session, synthesised answer, quiet until spoken), the liveness guards, and permissions announced aloud but decided by text.
- (note) The room split on the first two tickets: the join retires the three unknowns that can kill the feature (browser automation, canvas as camera, anonymous admission) while the gate is pure and testable under fakes with no browser, Signal or opencode. Host recommendation: the join as the tracer bullet, the gate second.
